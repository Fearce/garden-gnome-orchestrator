# Task worktrees — guidance for a shared repo, never a forced move

Built 2026-10-01 (`efc48b7`) as a FORCED move: every new task went into its own worktree at start. Before that, every task in a repo shared one working tree, a 33-hour Vota task blocked all other Vota work, and agents had to stage hunks around each other. On **2026-10-02 the owner made it guidance**. A task alone in its repo worked in a worktree for nothing, and agents (a QA agent reading a rebased Vota branch) burned their round reconstructing which worktree had done what. Now an agent claims a worktree only when another agent shares the repo. The owner's global `CLAUDE.md` (Branching section) and memory `feedback_one_task_one_branch_worktree.md` carry the machine-wide version.

## The model
- **GGO never moves a task.** `prepareTaskWorkspace` (threadManager, called at the top of `runPipeline` and on read-lane escalation) only re-attaches recorded worktrees whose folders are gone, and records `stageOutputs.workspaceMode` once: `guided` in a repo's main checkout, `umbrella` in a non-git folder holding repos, `in-place` for anything else (not git, or a worktree the owner made and pointed the task at). `worktree` is the retired forced mode; rows from 2026-10-01/02 still carry it, with `thread.workspace` inside their worktree, and their kickoff reads as before. Rows from before any of this have `homeWorkspace` null, get no mode and work in place forever.
- **Who hears the guidance:** top-level, non-read-lane tasks with `homeWorkspace` set and the setting `taskWorktrees` on (Settings › Pipeline). Off: no mode, no section. Sub-tasks and shotgun collaborators follow their parent (`worktreeSection` with `borrowed`): its claimed worktree, or no section while it works in the main checkout. They get no office advice, and their own `task_worktree` call on a guided repo is refused while the parent is unclaimed: the claim would land on the parent and split the child's work from the parent's.
- **Where the guidance is said:** the guided kickoff section (`worktreeBriefing.ts` `guidedBriefing`) says work here while alone, claim a worktree with `task_worktree` before the first edit when another agent shares the repo, and stay and commit only your own hunks if you already have edits. A branch the brief or the owner names outranks all of it: the agent works on that branch where it is checked out and claims nothing (the 2026-10-02 complaint: "I told this agent to work on my current branch and still he made a separate branch"). CLI backends get the exact `git -C <repo root> worktree add -b ggo/<name>-<id8> <repo>.worktrees\<name>` command. `officeNote` (kickoff, when peers are present) and `pushOfficeActivation` (the mid-run "teammate just joined" push) append `worktreeAdvice` for an editing agent whose task is guided and unclaimed. An agent that already has its own worktree reads "you meet only when integrating" instead of "you share this workspace".
- **A claim never moves `thread.workspace`.** `claimTaskWorktree` records the worktree in `thread.worktrees` and leaves `workspace` alone, because the Claude CLI stores a session's transcript in a per-cwd project folder: moving it would strand every later resume (QA fix rounds, cap failover). So everything that must see the claimed work follows `thread.worktrees` explicitly:
  - the Changes view, the code-context bar, the implementor's no-progress fingerprint and the resume handoff's git block: `taskWorkCheckout(thread)` (taskWorktree.ts) maps into the claimed worktree of the dispatched repo, diffed from its `baseSha`;
  - deliverable containment: `resolveTaskDeliverable` accepts an absolute path inside any claimed worktree, at all five call sites (bus, CLI bridge, the serve route, dedupe, the unsurfaced-artifact check);
  - later kickoffs (QA rounds, resumes): the guided section names the claim with its integration step.
  A new site that reads `thread.workspace` to find the task's WORK (not its cwd) needs the same treatment.
- **`<name>` names the work, never the title.** The agent passes its own `name` to `task_worktree`; omitted, `worktreeNameFromBrief` (`worktreeName.ts`, one Haiku call on the brief, 15 s cap, commentary-guarded) names it, falling back to the title slug on no token or a bad reply. The title alone produced `ggo/we-have-another-agent-working-in-5ec874c0` for "Improve email extraction rate in web crawler" (2026-10-01), because at first start it is still the prompt's truncated first line. Don't add a "rename the worktree later" path: sessions are keyed by cwd, and Windows refuses to rename a live process's cwd anyway. The folder is the name without the `-<id8>` suffix (`worktreeFolderName`); a clash gets `-2`.
- **`task_worktree(repo, name?, branch?)`** (implementor and QA, `claimTaskWorktree`) creates or returns the task's worktree for one repo and records it on the parent when a sub-task calls it. CLI backends (Codex/Grok) have no bus tool; `syncHandMadeWorktrees` (from `publishState` on qa/review/done/paused) discovers their `ggo/*-<id8>` worktrees off a guided task's repo or an umbrella's child repos.
- **Integration lives in the kickoff, not in GGO:** the own-worktree lines tell the agent to rebase onto the base, fast-forward the base (`merge --ff-only` in the main checkout, or `git fetch . branch:base`), and push when auto-push is on. In a commit-only (Vota) repo the work stays committed on the task branch. QA's fresh rounds get the same section.
- **A Co-worker turn holds every task dispatched to its checkout** (`coworkBlocks`): tasks start there now, so none is exempt as "moving out".

## Traps that already cost something
- **`git worktree remove` follows a junction and empties the MAIN checkout's `node_modules`.** `provisionWorktree` junctions every ignored `node_modules`/`.venv`/`venv` (in this repo that means `relay/`, `server/` and `web/`), so `retireTaskWorktree` unlinks every symlink among the worktree's ignored entries FIRST. That covers the recorded `links` and any junction an agent made by hand, because a discovered umbrella worktree has `links: []`. The revert-check proved it: with only recorded links unlinked, `test:task-worktree` F deletes the main checkout's package. Agents are told never to run `git worktree remove` themselves. To clean up stale worktrees by hand, do the same: `fs.unlinkSync` every symlink under the folder, then `git worktree remove --force`.
- **Retirement is conservative.** It runs at close/dismiss/purge (`retireWorktreesOf`) and removes the folder only when `git status` is clean and no deliverable lives inside. It deletes the branch only when it is merged into its base or never moved. An unmerged branch is the owner's work and stays. `ensureWorktreesPresent` re-attaches the branch on resume, retry, QA or auto-review.
- **Gates dispatch into THIS checkout.** The setting defaults on only for the server's own DB (`Db.isServerDb`, i.e. `config.dbPath`). Before that fix, every `vanilla-lane`/`route-pipeline` run cut real `ggo/*` worktrees beside this checkout, and the slow `git worktree add` raced the harness's dispose ("database connection is not open"). A gate that needs worktrees opts in with `mgr.setSettings({ taskWorktrees: true })` on throwaway repos, as `test:task-worktree-pipeline` does.
- **A fresh task worktree has no `server/dist` or `web/dist`**, so `test:gates` there fails `test:park-classify` (imports from dist) and `test:doc-paths` (docs cite `dist/.build-info.json`). Run `npm run build --prefix server` and `npm run build --prefix web` in the worktree first; both are gitignored.
- **Deploying GGO from a task worktree is refused** (`deploy.cjs` `refuseLinkedWorktree`): prod runs the main checkout's `dist`. Integrate first, then run `npm run deploy --prefix server` from the main checkout.

## Gates
`npm run test:task-worktree` covers the git layer and the briefing against real repos. `npm run test:task-worktree-pipeline` covers the mode decision (no task is moved), claims and what follows them (kickoff, Changes view, deliverables), sub-tasks, read lanes, restore, umbrella and hand-made discovery, the Co-work hold, the office advice and retire-on-close. `npm run test:worktree-name` covers the brief namer's parsing, commentary guard and fallbacks with the model stubbed. `test:deploy-plan` covers the linked-worktree guard. `npm run task-branch-lab --prefix server` is a browser lab: it renders the header's branch line for a worktree task and an in-place task at desktop and phone width, and flips the setting. For uncommitted work, run it with `GGO_LAB_ENTRY`/`GGO_LAB_WEB_DIST` as described in `lab-harness.cjs`.
